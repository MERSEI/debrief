# Debrief

Записывает рабочий созвон на Windows **двумя отдельными дорожками** и превращает
его в структурированный протокол встречи: договорённости, обязательства сторон,
открытые вопросы, красные флаги, цитаты с таймкодами.

Работает без бота-участника в конференции: звук берётся с самой машины, поэтому
Zoom, Meet, Telegram и Discord одинаково безразличны.

## Почему две дорожки

Обычный подход пишет один смешанный поток и затем пытается разделить голоса
диаризацией. Это вероятностный шаг, и он ошибается ровно там, где дороже всего —
на перебиваниях и коротких репликах.

Debrief пишет микрофон и системный вывод (WASAPI loopback) в два файла. Дорожка
микрофона — это всегда «я», дорожка loopback — всегда «собеседник». Спикер
известен точно, без модели и без порогов похожести голосов.

Взамен появляется эхо: если звук идёт в колонки, микрофон переспрашивает
собеседника, и одна фраза попадает в обе дорожки. Это лечится в
`debrief/transcript.py` — сегмент считается эхом, только если он одновременно
перекрыт по времени и текстуально похож на оригинал. Оба условия обязательны:
перекрытие без похожести — это обычное перебивание, и терять его нельзя.

### Тишина, которую приходится дописывать

WASAPI loopback молчит буквально: пока через устройство вывода ничего не
играет, поток не отдаёт буферов вообще — не нули, а ничего. Наивная запись
даёт файл, где первая реплика собеседника стоит в позиции 0, хотя прозвучала
на третьей минуте, и весь замысел с общей осью времени рассыпается.

Поэтому `debrief/audio/timeline.py` добивает пропуски цифровой тишиной,
сверяясь с монотонными часами. Проверено на живой записи: собеседник молчал
первые 5 секунд, речь легла на 8-ю — ровно туда, где прозвучала, а дорожки
разошлись на 15 мс за 12 секунд.

## Установка

```bash
pip install -e ".[capture,dev]"
cp .env.example .env   # заполнить ANTHROPIC_API_KEY
```

Требуется Python 3.11+ и Windows для захвата. Разбор уже записанных дорожек
(`debrief process`) работает на любой ОС.

`.env` подхватывается сам; уже заданные переменные окружения он не перетирает.

`faster-whisper` скачивает модель при первом запуске: `small` — около 500 МБ,
`large-v3` — около 3 ГБ. Скачивание идёт молча и занимает минуты, так что
первый прогон выглядит как зависший.

### Про устройство и скорость

`DEBRIEF_WHISPER_DEVICE=auto` пробует GPU, затем процессор, и берёт первое,
что реально поднялось. Это не перестраховка: наличие видеокарты не означает,
что на ней получится считать — ctranslate2 видит устройство через драйвер, а
считает через cuBLAS, который ставится отдельно. На такой машине конструктор
модели проходит молча, а падает первое вычисление, поэтому после загрузки
прогоняется секунда тишины: пусть устройство откажет сразу, а не посреди
разбора часового созвона.

Явно названное устройство (`cuda`) фолбэка не получает — если вы его назвали,
вам нужно знать, что оно не работает, а не получить молча вдесятеро более
медленный прогон.

Замер на 12-ядерном процессоре, модель `small`, `int8`: **9.9× быстрее
реального времени** — часовой созвон распознаётся примерно за 6 минут.

## Использование

```bash
debrief devices                          # проверить, что именно будет записано
debrief record --hint "собес на Python"  # запись; Ctrl+C — стоп и разбор
debrief record -d 1800                   # запись ровно 30 минут, без клавиатуры
debrief process recordings/сессия.mic.wav
```

`--hint` заметно улучшает разбор: без него модель не знает, чья сторона какая,
и трактует разговор нейтральнее, чем нужно.

Начинайте с `debrief devices`. Если loopback не нашёлся, звук идёт мимо WASAPI —
разбираться нужно там, а не в записи.

## Как устроено

```
запись           debrief/audio/    два потока WASAPI -> два WAV с общим нулём времени
распознавание    debrief/stt/      faster-whisper по каждой дорожке отдельно
склейка          debrief/transcript.py  эхо-фильтр, слияние по общей оси времени
разбор           debrief/summarize.py   Claude + Pydantic-схема ответа
выдача           debrief/sinks/    Markdown в Obsidian, карточка в Telegram
```

Схема протокола валидируется на стороне API (`client.messages.parse`), а не
парсингом markdown из текста ответа. Промпт запрещает достраивать смысл: пустой
раздел — нормальный результат, выдуманный — брак.

## Ограничения

- Захват только Windows: WASAPI loopback — механизм этой ОС.
- Запись разговора со второй стороной регулируется законом и различается по
  юрисдикциям. Для личных заметок это одно, для продукта — нужен явный флоу
  уведомления собеседника.
- Разбор стоит денег: примерно цена одного запроса Claude на созвон.
  Распознавание — локальное и бесплатное.
- Если разбор не состоялся — нет ключа, кончился лимит, модель отказала —
  стенограмма всё равно сохраняется в заметку вместе с командой для повтора,
  а команда возвращает код 1. Терять получасовой созвон из-за сбоя сети нельзя.

## Что проверено на живом железе

Не «должно работать», а прогнано:

- захват обеих дорожек, Realtek 44.1 кГц (микрофон) и 48 кГц (loopback);
- синхронность дорожек — расхождение 15 мс на 12 секундах записи;
- заполнение тишиной при молчащем loopback — 5 секунд молчания встали на
  своё место, речь не сдвинулась;
- сквозной прогон с синтезированной русской речью: все четыре реплики
  распознаны, таймкоды совпали с измеренными уровнями сигнала;
- откат с непригодного GPU на процессор;
- сохранение стенограммы при недоступном разборе.

Не проверено вживую: сам разбор через Claude (нужен ключ) и длинные записи —
всё измеренное выше в пределах минуты.

## Тесты

```bash
pytest
```

35 тестов на ядро: слияние дорожек и эхо-фильтр, удержание общей оси времени,
выбор устройства для Whisper, рендер протокола, нарезка длинных сообщений для
Telegram. Сам аудиозахват и вызов модели тестами не покрыты — они проверены
прогоном на железе, см. раздел выше.
